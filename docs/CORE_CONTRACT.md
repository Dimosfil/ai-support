# Контракт основы поддержки v1

## Поставка и источник истины

Первая реализация — встраиваемая ESM-библиотека Node.js с отдельными SQLite и
HTTP-адаптерами. Продукт включает фиксированную версию исходников/пакета и
использует собственную серверную сессию. Соседние репозитории не читаются.
Локальный HTTP-процесс — стенд для разработки, а не обязательная форма поставки.
Пакет пока private: публикация в registry не настроена.

SQLite — источник истины обращений, сообщений, назначений, версий, аудита,
намерений уведомления и результатов повторов. Identity и полномочия принадлежат
продукту. Идентификаторы бизнес-объектов и события диагностики не заменяют тикеты.
Время хранится как Unix milliseconds UTC, текст — Unicode.

HTTP-контракт версионируется `/api/v1`; схема хранилища — `PRAGMA user_version`.
При неизвестной версии схемы запуск прекращается. Поддерживаются v1 и v2:
новая БД создаётся в v2, существующая v1 работает без доставки и не мигрируется
при старте. Для G2.2 есть отдельная offline-миграция с backup и проверкой
восстановления; [порядок и контракты](NOTIFICATIONS.md).

## Владельцы и границы

| Граница | Вход и результат | Владелец | Реализация |
| --- | --- | --- | --- |
| Identity | Серверный запрос → `{tenant,subject,role}` или отказ | Продукт | HTTP вызывает `authenticate(request)` при каждом запросе; локальный адаптер проверяет случайный bearer key |
| Ядро | Principal + команда → receipt либо `SupportError` | `SupportService` | Права, нормализация, статусы, повторы, лимит записей |
| Repository/unit of work | Синхронная транзакция → все записи либо rollback | `SqliteStore` | SQLite, FK, WAL, FULL synchronous, optimistic version |
| Business context | Проверенный product reference → разрешённые ссылки | Продукт | Отложено до G2; клиентский произвольный контекст отклоняется |
| Diagnostics | Закрытая ссылка → очищенное техническое событие либо отсутствие | Продукт | Отложено до G2, не участвует в сохранении обращения |
| Attachment storage | Проверенный principal + attachment reference → доступ/удаление | Продукт | Выключено; загрузки, скачивания и attachment IDs в командах не принимаются |
| Delivery | Notification intent + актуальные права/настройки → результат попытки | NotificationDispatcher / host adapters | G2.2: SQLite leases/попытки, Telegram/product transports; каталог и актуальные права даёт продукт |

Производственный identity-адаптер обязан проверять аутентичность, актуальность
сессии, принадлежность продукту и операторские полномочия. Нельзя строить principal
из `X-Role`, `X-Tenant`, account ID, полей формы или непроверенного JWT payload.
Встраиваемый вызов считает principal уже проверенным доверенным сервером;
не передавайте в него значения напрямую из пользовательского запроса.

После включения фиксированной версии пакета продукт использует
`SupportService`/`SqliteStore` из `@ai-support/core`; опциональный HTTP-адаптер
доступен как `createHttpServer` из `@ai-support/core/http`. Передайте ему service
и собственную функцию `authenticate(request)`. Иначе вызывайте методы service
из своих серверных контроллеров. Функция аутентификации может быть асинхронной;
callback SQLite-транзакции всегда синхронный. Вызов ядра не запускает listener.

## Операции

- `create(principal, {subject,body}, key)` — только user; владелец всегда текущий
  subject. Возвращает `{id,version,messageId,replayed}` после commit.
- `list(principal, {before?,limit?})` — новые обращения первыми; user видит свои,
  operator — очередь своего tenant. `get(principal,id)` проверяет ту же область.
- `messages(principal,id,page)` — новые сообщения первыми. Внутренние заметки
  исключаются до пагинации для user. UI разворачивает текущую страницу по времени.
- `audit(principal,id,page)` — только operator своего tenant. Аудит содержит
  действия, авторов, версии через порядок операций и переходы; не копирует тело
  переписки. Удаление сообщений и редактирование истории не предусмотрены.
- `change(principal,id,command,key)` — каждая команда требует текущую `version`.
  `type:message` принимает `body,visibility` (public по умолчанию); internal
  доступен только operator. `type:status` принимает `status`; `type:assignment`
  принимает `assigned:boolean`. Последние две команды доступны operator.
  Назначить можно себя либо снять назначение, произвольный ID сотрудника не принимается.

Размер страницы: 1–100, по умолчанию 30. `before` — положительный целый `seq`
последнего элемента предыдущей страницы, исключительная верхняя граница.
Ответ: `{items,nextCursor}`, `nextCursor:null` завершает обход. Новые записи не
сдвигают старые страницы. Номер `seq`, UUID и cursor не предоставляют доступа.

## Статусы, версии и повторы

Разрешены переходы: new → in_progress/resolved;
in_progress → waiting_user/resolved; waiting_user → in_progress/resolved;
resolved → in_progress. Пользовательский ответ в waiting_user или resolved
автоматически возвращает in_progress и записывает переход в аудит.
Операторский ответ сам по себе не решает вопрос и не переводит в waiting_user.
Внутренняя заметка не меняет статус. Автоматического закрытия нет.

Каждое изменение увеличивает версию. Несовпадение даёт `409 version_conflict`
без сообщения, аудита или notification intent. Клиент обновляет историю и решает,
нужно ли повторять действие; сервер не перетирает новую версию старым запросом.

Ключ повтора обязателен: 8–128 символов `[A-Za-z0-9_-]`. Область: tenant,
subject, операция (`create` либо `change:<ticketId>`), ключ. Fingerprint считается
по нормализованной команде, включая исходную версию. Повтор возвращает исходный
receipt, не создаёт новые записи и не расходует лимит. Другое содержимое даёт
`409 idempotency_conflict`. Обычная одинаковая новая команда с новым ключом —
новая операция. Срок удаления receipt пока не задан: они сохраняются вместе с БД.

Изменение тикета, сообщение, аудит, notification intent и receipt выполняются
одним commit. Ошибка любой записи откатывает весь результат. После потери ответа
клиент повторяет исходную команду с тем же ключом и версией, даже если тикет уже
изменился. Права проверяются заново до replay. Receipt не содержит текста заметок.

## Политики первой версии

- Роли: user и operator, обе ограничены tenant. User не меняет статусы и
  назначения; аудит доступен только operator. Admin/удаление/массовые действия
  пока не реализованы. Продукт сам решает, кому выдавать роль operator.
- Гостевой приём выключен. Нет подтверждённого обратного контакта, антиспам-потока
  и привязки гостя к аккаунту; до их реализации anonymous получает 401.
- Вложения выключены. До включения требуется определить allowlist форматов,
  лимиты, проверку содержимого, закрытую выдачу, удаление, retention и аудит.
- Текст: тема до 200, сообщение до 10000 символов; значения задаются политикой.
  Durable лимит по tenant+subject: 20 созданий/сообщений за скользящую минуту,
  включая заметки. HTTP-адаптер дополнительно ограничивает входящие запросы по IP.
- Нет автоматической очистки и обещанного SLA. Локальные данные сохраняются в
  закрытой БД до явного обслуживания. До работы с реальными пользователями
  продукт должен определить сроки хранения, удаление, backup и доступ персонала.
- Неподключённые возможности возвращаются в session capabilities как false.
  Сохранение intent означает «уведомление запланировано», а не «доставлено».
  Внутренние заметки никогда не формируют intent. Диспетчер G2 обязан заново
  проверять получателя и настройки, вести попытки и ограниченный backoff.

## Ограничения текущей поставки

Один локальный runtime, синхронный SQLite-адаптер. Фоновые сетевые запросы есть
только при явно включённой доставке; создание обращения их не ожидает.
Конкуренция двух worker на разных SQLite-соединениях проверена, но объёмные
очереди и распределённые установки не являются проверенным режимом.
`node:sqlite` в проверенном Node 24.14.1 выдаёт ExperimentalWarning; API изолирован
хранилищем и покрыт интеграционными тестами. Нужна повторная проверка при обновлении Node.
HTTPS, production sessions, живые получатели доставки, публичная помощь и
независимый аварийный контакт ещё не настроены. Реализация G2.2 в основе есть;
G1 целиком и этапы G2–G4 в реальном продукте не приняты.
