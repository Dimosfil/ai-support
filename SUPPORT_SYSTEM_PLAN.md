# Общая основа системы поддержки

Дата: 25.10.2026. Статус: реализована локальная основа G0/G1 и механизм G2.2; полная приёмка
этапов и подключение реального продукта ещё не выполнены.

Переносимая основа для обращений, переписки, очереди операторов, диагностики и
подключаемых каналов. Сначала выпускается сайт, затем Telegram с общей историей.
Основа отделена от продуктов. Первая форма поставки — встраиваемое ESM-ядро
Node.js с SQLite-адаптером и локальным HTTP/web-стендом. Production-хостинг
и необходимость отдельного защищённого сервиса уточняются при интеграции.
Текущий контракт: [CORE_CONTRACT.md](docs/CORE_CONTRACT.md).

## Разделение ответственности

| Общая основа | Адаптер продукта |
| --- | --- |
| Обращения, сообщения, статусы, назначение и аудит | Сессия, проверенная identity, аккаунты и операторские полномочия |
| Каналы, доставка и защита от повторов | Привязка Telegram и настройки уведомлений |
| Ссылки на бизнес-объекты и ошибки | Задачи, платежи и очищенный диагностический контекст |
| Интерфейс вложений и проверки доступа | Хранилище файлов, ограничения и сроки хранения |
| Инциденты и связанные обращения | Классификация ошибок и определение затронутых пользователей |
| Версионируемые контракты и сценарии совместимости | Оформление, локализация, регламент и резервный контакт |

Основа не выполняет бизнес-операции продукта и не знает его таблиц, провайдеров,
тарифов и секретов. Соседний исходный каталог не становится зависимостью runtime
или сборки: поставляется фиксированная версия пакета/исходников либо используется
явно настроенный защищённый API. Полный внешний сервис не обязателен для первого сайта.

## Пользовательский и операторский сценарии

1. Пользователь открывает поддержку в меню или возле ошибки, описывает проблему
   и явно добавляет вложения. Сервер прикладывает разрешённый контекст.
2. Только после устойчивого сохранения пользователь получает номер и «Принято».
   Потеря ответа допускает повтор с тем же ключом без второго обращения.
3. Оператор видит очередь, контекст, ответственного и переписку. Публичные
   ответы и внутренние заметки имеют разную видимость.
4. Ответ сохраняется до постановки уведомления на доставку. Отказ внешнего
   канала не теряет сообщение; интерфейс различает сохранение и доставку.
5. После запуска Telegram пользователь выбирает обращение и продолжает ту же
   переписку. Отключение бота не нарушает работу сайта.
6. При массовом сбое оператор связывает обращения с общим инцидентом и сообщает
   проверенные сведения о ходе решения и результате.

## Данные и инварианты

Логические сущности: продукт/tenant, проверенная identity, обращение, сообщение,
вложение, ссылка на бизнес-объект/диагностику, инцидент, настройки уведомлений,
попытка доставки и аудит. SQL-схемы и HTTP-маршруты уточняются при реализации.

- Продукт, владелец и полномочия проверяются при каждой операции, загрузке файла
  и фоновой доставке. Клиентский account ID и номер обращения не дают доступ.
- Ключ повтора ограничен продуктом, субъектом и операцией; повтор с другим
  содержимым отклоняется. Входящие updates Telegram дедуплицируются по update ID.
- Принятые сообщения и очередь уведомлений устойчивы к перезапуску. Доставка
  имеет ограниченные повторы и backoff. Неизвестный результат внешней отправки
  учитывает возможный дубль; exactly-once без гарантии внешнего API не обещается.
- Внутренние заметки не попадают в пользовательскую историю или уведомления.
- Поддержка не требует покупки, баланса или доступа к основным платным функциям.
- Support-режим бота отделён от команд и черновиков основного продукта.
- Конкурентные назначения/ответы проверяют версию записи и не перетирают изменения.

Статусы: `new` → `in_progress` → `waiting_user` → `in_progress` → `resolved`.
Оператор может решить вопрос без уточнений. Сообщение пользователя в `waiting_user`
возвращает `in_progress`, в `resolved` — открывает вопрос повторно с аудитом.
Дубли связываются без удаления переписки. Приоритет, ответственный, инцидент и
доставка — отдельные поля. Сроки окончательной архивации задаёт продукт;
автоматического закрытия по таймеру по умолчанию нет.

## Диагностика и приватность

Техническая ошибка, пользовательское обращение и массовый инцидент различаются.
Автосбор не создаёт тикет на каждое событие. Закрытая связь с диагностикой
использует непредсказуемый код и проверку доступа; событие может отсутствовать.
Группировка учитывает очищенный fingerprint, версию, этап и временное окно;
одинаковый текст сам по себе не доказывает общую причину.

Диагностический сервис получает только разрешённые технические поля. Текст
переписки, контакты и вложения остаются в закрытом контуре поддержки. Не собираются
пароли, cookie, токены, платёжные реквизиты, произвольные тела запросов, запись
экрана и нажатия клавиш. До открытия вложений определяются доступ, форматы/размеры,
обработка опасного содержимого, сроки хранения, удаление и аудит.

Гостям доступен ограниченный приём вопросов и проблем входа с защитой от спама.
Гостевое обращение не открывает данные аккаунта; связывание требует проверки.
Для ответа вне текущего окна нужен проверенный обратный контакт. Неподключённый
канал не показывается рабочим. Публичная помощь не требует сессии; резервный
контакт/страница состояния должны иметь проверенный путь независимо от основного API/БД.

## Отложенные решения

Production-инфраструктура, SLA, сроки хранения, резервный контакт и необходимость
отдельного сервиса выбираются при интеграции. Автономный AI-оператор,
автоматические компенсации, внешняя CRM и новые
платные сервисы не входят в первый выпуск.

Документация для повторной проверки при реализации:
[Telegram Bot API](https://core.telegram.org/bots/api),
[ограничения начала диалога](https://core.telegram.org/bots).
